# demo

两步流程：先"问"清楚产品（产出产品思考锚点 `docs/product/sense.md`），再"做"一组风格化 HTML demo 页面（产出 `docs/product/demo/`）。

## 核心规则（grilling 模式）

- **一问一答**：一次只问一个问题，等用户回答后再继续。不要一次抛多个问题。
- **每问附推荐答案**：给出你的建议，帮用户快速做决定。
- **事实靠查、决策靠问**：能从环境查到的（文件系统、已有文档等）先查再问；需要用户拍板的决策，逐个问。
- **达成共识前不写文件**：sense.md 和 demo 都在用户确认后再生成。
- **用户答不上来时**：基于已收集的上下文给出你的推荐假设，标注"（假设）"，继续往下走。
- **关键决策不许静默悬空**：影响 demo 形态的次要决策（风格、细节取舍等），用户若答"不确定/纠结"，给推荐 + 理由、标"（假设）"作为工作结论继续，并在 sense.md「待确认」留档。**结构性决策（平台、核心形态）例外**：它们决定核心体验与竞争力，必须 push 到用户拍板的结果，不许用（假设）顶替带过。

## Phase 1 — 摸清产品（grill）

按**产品推演脉络**推进：先立题（值不值得做）→ 挖用户与问题（给谁、痛在哪）→ 定方案与本质（怎么做、是什么）→ 走旅程与落地（怎么用、在哪落地）→ 对照竞争与差异（凭什么）→ 立价值与愿景（相信什么、做多大）→ 验证商业与风险（怎么活、怎么死）。每一环收敛出结论再进下一环。

**结论循环（每环通用 6 步，能咬合的都用上）：**
1. **ask**：一次一问，附推荐答案。
2. **启发**：不只给答案，还开方向——举例子、给选项、抛思路，帮用户从"不知道"到"有的想"。
3. **对抗**：质疑答案——反例/边界、事实还是推断、和前面结论矛盾吗、凭什么。
4. **第一性原理**：剥离形态回到本质——用户真正要达成的 job 是什么、达成它的最短路径是什么、产品本质上是什么对象。
5. **联网搜索**：答案里可查证的事实点，用 WebSearch 验证（每环给了具体搜法）；查不到就明说"搜索受限，仅按用户认知记录"，不编造来源。
6. **验证**：结论标成【事实】/【假设】/【待定】，与之前环节交叉核对，冲突当场对齐。

标不出【事实】的至少给出带理由的【假设】；所有结论落盘 sense.md 对应章节。

### 1.1 立题 · 前提挑战（先确认值不值得做）

先请用户用一句话讲这个想法（调用时已给就复述确认）；再走结论循环把三点问破，别接受第一版说法就往下：

1. **本质问题**（第一性原理）：剥离形态，这个产品要解决的"本质问题"是什么？它帮用户达成什么 job？
2. **换框架**（对抗）：换个视角看这个问题，会不会有更简单、更有力、或完全不同的解法？（如"工具"→"服务"、"产品"→"社区"）
3. **什么都不做**（对抗）：如果今天不做，目标用户的痛点还在吗？是真实需求还是想象的？有多痛、多频繁？

→ 结论写进 sense.md「一、前提挑战」：采纳/否决哪个框架、为什么；不做时痛点是否仍在。

### 1.2 用户与问题（从人出发）

1. **目标用户**（ask+启发）：核心用户是谁？现在怎么解决这个问题？（现状 = 隐藏竞品）
   - 对抗：这是真实人群还是画出来的画像？谁最痛、最值得先服务？
   - → sense.md「二、目标用户」
2. **用户痛点**（ask+启发+联网）：痛在哪、多痛、多频繁？
   - 启发：给痛点维度（效率/成本/情绪/风险/机会损失……）
   - 联网：搜 `<问题> 用户 抱怨/痛点`，验证有真实呼声还是想象
   - → sense.md「三、用户痛点」
3. **要解决的问题**（ask+收敛）：一句清晰的问题陈述
   - 对抗：这句话能证伪吗？产品做出来，怎么知道问题解决了？
   - → sense.md「四、要解决的问题」

### 1.3 方案与本质（怎么做、是什么）

1. **解决方案**（ask+对抗+联网）：打算怎么解决？
   - 第一性原理：达成用户 job 的最短路径是什么？方案绕远了吗？
   - 对抗：逼出 ≥1 个备选，比较各自代价，别拿第一个答案就写
   - 联网：搜 `<问题> 怎么做/方案`，看是否已有现成做法，避免重复造轮子
   - → sense.md「五、解决方案」
2. **产品品类**（ask+启发+联网）：这属于哪类产品？
   - 启发：给品类候选（工具/社区/服务/平台/内容……）
   - 联网：搜 `<品类> 产品 有哪些`，品类真实存在吗？已被占满吗？
   - → sense.md「六、产品品类」
3. **一句话定位**（ask+收敛）：用一句话说清"这是什么、给谁、带来什么"
   - 对抗：这句话换到竞品身上也成立吗？成立就是没定位
   - → sense.md「七、一句话定位」

### 1.4 旅程与落地（用户怎么用、在哪用）

1. **核心用户旅程**（ask+启发）：用户从进入到获得价值的几步
   - 启发：给常见旅程骨架（发现→上手→核心动作→获得价值→回流）
   - → sense.md「八、核心用户旅程」
2. **核心主脉络（28 定律）**（ask+对抗）：承载 80% 价值的 20% 核心功能
   - 对抗：砍到只剩这 20%，用户还能获得价值吗？砍不掉的才是主脉络
   - → sense.md「九、核心主脉络」
3. **平台形态**（ask，AskUserQuestion 单选）：web / H5 / 小程序 / 手机App / 客户端 —— **结构性决策，必须 push 到拍板，不许兜底带过**
   - 启发：给每个平台的取舍框架——web/H5（零安装易传播、留存弱）、小程序（微信生态低门槛、体验受限且数据归平台）、手机App（体验/推送最强、下载门槛高）、客户端（能力最强、分发难）
   - 第一性原理：把问题从"哪个平台"换成"**哪个平台才能让核心体验与竞争力成立**"——推送=App、微信社交裂变=小程序、专业桌面工具=客户端；先想核心体验绑在哪个平台
   - 对抗：拆开你的纠结点（成本/传播/体验/开发），逐项逼决策，别整体悬着
   - 联网：搜同类产品分别选了哪个平台、为什么——竞品的平台选择就是竞争信号
   - 拍板：给出明确推荐 + 理由，要求用户定；仍犹豫就按拆出的纠结点逐个逼，**不许以"待定"带过**
   - → sense.md「十、产品形态（平台）」只填拍板结果

### 1.5 竞争与差异（凭什么）

1. **竞品**（ask+对抗+联网）：市面上相似的产品？各自怎样？
   - 对抗：它做得好不好？有没有查到你设想重叠的玩家？
   - 联网：搜 `<品类> 竞品` 或 `<category> landscape <今年>`；对每个已提名竞品至少查证一件：做的是什么、优缺点
   - → sense.md「十一、竞品分析」（区分【用户认知】/【查证所得】，附来源）
2. **差异点**（ask+对抗+联网）：你希望做到不一样的是什么？
   - 对抗：凭什么是你——一个周末能抄走的差异不是差异（要有防御性）；为什么是现在，早一年/晚一年会怎样？
   - 联网：搜 `<差异点> 产品`，验证"差异化"是不是真差异、是否已有产品在做
   - → sense.md「十二、差异点」

### 1.6 价值与愿景（相信什么、做多大）

1. **产品理念**（ask+收敛）：这个产品相信什么？存在的理由、核心主张
   - 启发：把前面环节的结论收敛成一句理念（不是口号，是立场）
   - → sense.md「十三、产品理念」
2. **10x 愿景**（ask+启发）：如果做到极致，12 个月后这个产品长什么样？
   - 启发：给"更夸张但可想象"的版本，帮用户跳出今天的形态
   - → sense.md「十四、10x 愿景」

### 1.7 商业与风险（怎么活、怎么死）

1. **成功指标**（ask+第一性原理）：怎么衡量做对了？
   - 第一性原理：指标必须能证伪"问题被解决了"，定 1 个北极星 + 2-3 个辅助
   - → sense.md「十五、成功指标（北极星）」
2. **商业模式**（ask）：怎么活下来？（订阅/增值/其他，或标"待定"）
   - → sense.md「十六、商业模式 / 变现路径」
3. **逆向问题 / 风险依赖**（ask+对抗）：什么会让它失败？
   - 对抗：Munger 逆向——先想怎么失败，再倒推要防什么；外部依赖、假设不成立的后果
   - → sense.md「十七、逆向问题 / 风险与依赖」

### 1.8 完成度门禁（MECE 自检，缺就补一轮）

收敛成摘要前，用 MECE 过一遍完整性，缺就补问：
- **用户/问题**：目标用户、痛点、问题陈述齐了吗？
- **方案/本质**：解决方案（含备选）、品类、定位齐了吗？
- **旅程/落地**：用户旅程、主脉络齐了吗？平台**已拍板**了吗？（平台是结构性决策，不许用（假设）顶替）
- **竞争/价值**：竞品查证过、差异有防御性、理念、愿景齐了吗？
- **商业/风险**：指标、变现、逆向/依赖齐了吗？
- **标注**：每项都标了【事实】/【假设】/【待定】吗？假设必须可见
- **素材**：现在去 demo 3 页（Phase 2），主脉络 / 用户旅程 / 核心功能各对应得上哪页？

有缺就补一轮 grill，再进入确认。

## Phase 2 — 风格化 demo（先比风格，后定稿）

两步：先用**同一产品**做 3 套不同风格的诠释同屏对比，让用户选定一套风格；再用选定风格生成完整 3 页页面组。三份共享同一产品与代表页主题，文案/结构/布局各自发挥——比的是风格与整体气质，不是逐像素差异。

### 2.1 选代表页

基于 sense.md「核心主脉络 + 核心用户旅程」，选一张最能代表产品的核心页（如承载主脉络的那张）作为**风格代表页**；其余页面留到定稿时生成。

### 2.2 选 3 套风格（从风格池）

从下面的**风格池**里，按产品调性推荐 3 套做对比，给出推荐理由；用户可点名替换任意一套，或"都不合适，按我描述自定义"。文件用风格 slug 命名。

风格池共 16 套，**每套一个独立配方文件** `styles/<slug>.md`（生成时只载入选中的那几份，避免配方互相串味、浪费上下文）；配方按下面的 7 槽位模板填写。下表为速查。

| 风格 | slug | 适合调性 |
|------|------|----------|
| Apple 极简 | apple-minimal | 高端消费、iOS 概念、通用高端 |
| 简约现代 | minimal | 效率工具、B 端、通用 |
| 毛玻璃 | glass | 年轻向、AI、社交 |
| 高级感 | luxury | 金融、理财、会员 |
| 液态玻璃 | liquid-glass | 高端科技、AI、旗舰产品 |
| 安静奢华 | quiet-luxury | 高端品牌、理财、B 端旗舰 |
| 杂志质感 | editorial | 内容平台、生活方式、时尚 |
| 触觉立体 | volumetric | 消费、工具、年轻品质向 |
| 宝石色调 | jewel | 高端消费、会员、品牌精品 |
| 新拟态 | neumorphic | 工具、健康/冥想 |
| 霓虹赛博 | neon | 游戏、潮流、Web3 |
| 和风禅意 | zen | 文化、生活、手工 |
| 明快多彩 | playful | 儿童、社交、消费 |
| 手绘插画 | illustration | 教育、品牌、内容 |
| 复古纸张 | retro | 咖啡、书店、老字号 |
| 数据驾驶舱 | data | B 端、监控、分析 |

示例推荐组合：金融产品 → quiet-luxury + data + liquid-glass（或 luxury + minimal）；年轻社交 → playful + glass + neon。

**配方 = 7 槽位模板**（`styles/<slug>.md` 里每段 prompt 都按它填；自定义风格、新增风格也用它）：

| # | 槽位 | 作用 | 反例（含糊）→ 正例（具体） |
|---|------|------|---------------------------|
| ① | 具名参考风格 | 激活模型训练数据里的风格记忆，其余细节自动补全 | 「现代风格」→「Apple 极简 / Liquid Glass / 时尚杂志版式」 |
| ② | 具体色板 | 精确到色名 + hex，模型就不用自己发明默认蓝 | 「中性色+强调色」→「暖白 #F5F5F7、墨黑 #1D1D1F、柔和橙 #FF9F0A」 |
| ③ | 字体方向 | 指名衬线/无衬线/等宽 + 字体名 | 「优雅字体」→「SF Pro 风格系统无衬线」 |
| ④ | 质感词 | 阴影、圆角、间距、纹理、图标，给具体方向/数值 | 「细腻」→「1px 细边框、低模糊轻阴影、大圆角、大间距」 |
| ⑤ | 情绪词 | 编码配色与留白的坐标（宁静→低饱和、大留白） | 「好看」→「宁静、克制、安静、高端」 |
| ⑥ | 负向约束 | 显式剪掉模型最高频的翻车点 | （无）→「请勿添加时间/wifi 状态条、无需设备壳、不用默认蓝」 |
| ⑦ | 质量锚 | 给输出定档 | （无）→「作品集品质 / 出版物级 / 像真机」 |

**组装句式**（把 7 槽位拼成一段可直接投喂的话）：

> 设计一款适用于{载体}的{①风格}界面（使用 html 展示，无需模拟设备外壳，请勿添加时间、wifi 等状态条，尺寸由浏览器控制）。
> 该界面应呈现出{⑤情绪}，采用{②背景基调}，以及{布局}。使用{④质感}、{构图}和{排版}。
> 保持风格{风格关键词}。
> 使用：{③字体}、{②色板逐项}、{④质感逐项}、{⑥负向约束}、{⑦质量锚}

新增风格：`styles/` 下新建 `<slug>.md`（按 7 槽位填）+ 下表加一行。

### 2.3 生成 3 套风格代表页（同一产品 × 3 诠释，subagent 全自主）

用 **3 个 subagent 分开生成**，每个 subagent 只喂「产品 + 自己那一套 `styles/<slug>.md` 配方」，互不可见、**零共享**——没有共享骨架，也没有锁死的内容规格，文案/结构/布局/CSS 全部各自发挥。唯一共享的是产品本身：subagent 必须先知道自己是在给什么产品做 demo。

步骤：
1. **共享输入 = 产品（仅此而已）**：主会话按 2.1 确定代表页主题（如「首页」或「核心功能页」）作为共同主题。每个 subagent 的输入 = `docs/product/sense.md` + 代表页主题 + 自己那份 `styles/<slug>.md` 配方；除此之外各写各的，互不依赖、互不可见。
2. **并行派全栈 subagent**：对每个选中 slug 各派一个 subagent（`Agent` 工具并行），它自由决定文案、HTML 结构与 CSS，写出 `preview-<slug>.html` + `css/preview-<slug>.css`（先 `mkdir -p docs/product/demo/css docs/product/demo/js`）。不读其他风格文件。
3. 每套严格按自己配方生成，禁止跨风格借用视觉元素（色板/字体/质感/情绪）。

比较前提：从「同一页 × 3 风格」放宽为「同一产品 × 3 诠释」——三份内容可能不同，比的是整体气质与方向；若对比时觉得文案漂移干扰判断，恢复内容规格即可（主会话锁定逐字文案，subagent 只改结构/CSS）。

每份页面自成一套**设计令牌 + 共享组件**：
- 设计令牌（`:root` 自定义属性）：色板、字体栈、字号阶梯、间距、圆角、阴影、描边。
- 共享组件类：按钮、卡片、导航、标题区、栅格等。
- 用户自定义风格：按用户描述的视觉关键词推断具体设计令牌（给明确的颜色/字体/质感），不做模糊处理；自定义时按上面的 7 槽位结构追问补齐（具名参考 / 色板 / 字体 / 质感 / 情绪 / 负向约束 / 质量锚），缺槽位时先给推荐假设再落定。

### 2.4 对比页

`index.html` 用 iframe 把 3 个风格代表页**同屏并排**，顶部一条说明栏（每套风格名 + 一句话特征），方便一屏比风格。对比页自身用一套中性样式，不引入具体风格。

### 2.5 用户选定最终风格（AskUserQuestion，单选）

- 从对比的 3 套中选一 / 都不满意（按用户描述自定义）
- **附推荐**：按产品调性给一个（如严肃金融类 → 高级感）
- 选"都不满意"→ 按用户描述出一版，替换最弱的一版预览

### 2.6 用选定风格生成完整页面组（定稿）

选定风格后，把该风格的 CSS 定为 `css/style.css`（设计令牌 + 共享组件），基于 sense.md 生成完整 3 页：

- `page-01.html` ← 首页（定位/卖点）
- `page-02.html` ← 核心页（主脉络）
- `page-03.html` ← 价值页（行动/详情/CTA）

**规则**（两阶段通用）：
- CSS / JS 独立文件：每个 HTML 用 `<link rel="stylesheet" href="css/style.css">` 引入样式、`<script src="js/main.js">` 引入脚本，不内联样式与脚本。定稿页只引用 `css/style.css`。
- 预览页（`preview-*.html`）与预览 CSS（`css/preview-*.css`）**保留**作风格参照，不删——它们是"为什么当初选这个风格"的留档。
- 不加手机框/窗口框等设备 mockup：只做普通响应式页面；屏幕尺寸由浏览器窗口直接控制模拟。
- 每个 HTML 头部留注释 `<!-- 由 /simple:demo 生成 -->`。

**定稿后的文件结构**：

    docs/product/demo/
    ├── index.html            ← 对比页：3 套风格同屏（保留）
    ├── preview-<slug1>.html  ← 风格预览（保留参照）
    ├── preview-<slug2>.html
    ├── preview-<slug3>.html
    ├── page-01.html          ← 首页 · 定稿风格
    ├── page-02.html          ← 核心页 · 定稿风格
    ├── page-03.html          ← 价值页 · 定稿风格
    ├── css/
    │   ├── style.css         ← 定稿风格：设计令牌 + 共享组件
    │   └── preview-<slug>.css  ← 预览风格（保留参照）
    └── js/main.js            ← 共享交互（如需）
