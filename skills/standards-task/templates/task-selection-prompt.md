# 异步任务层选型（prompt 模板）

## prompt 模板

    你是一位资深后端工程师，精通{语言}和业务驱动开发。请你基于项目信息，对异步任务层进行技术选型分析
    （只做选型即可），各候选方案给出详细理由 + 替代方案对比表，并输出 task-layer-rule.md（约束）与
    task-layer-draft.md（分析）至 docs/standards/。

    ## 项目信息

    请阅读以下文件：
    - 业务流程描述：docs/product/business-flow.md
    - 技术选型：docs/standards/tech-stack-rule.md
    - 目录结构：docs/standards/directory-rule.md
    - 工具层：docs/standards/tools-rule.md

    ## 分析要求

    ### 一、问题背景
    1. **现状问题**：当前异步操作如何处理（如裸 goroutine / 直接同步 / 无队列），存在什么问题
       （无持久化 / 无重试 / 无可见性 / 无并发控制 / 不可扩展 / 错误处理粗糙）。
    2. **需求分析**：从 business-flow 与 handler 中识别异步候选场景（如调用外部 AI / 发送通知 /
       耗时计算 / 定时任务），明确异步方案必须满足：
       - 任务持久化（进程重启不丢失）
       - 自动重试（可配置次数、间隔）
       - 并发控制（防止外部依赖过载）
       - 可观测性（任务状态 pending/processing/completed/failed）
       - 多进程隔离（worker 与 HTTP server 独立）
       - 易于扩展（新增任务低成本）
       - 符合现有架构（不引入违背所选架构的抽象层）

    ### 二、候选方案对比
    1. **候选方案表**（方案 × 持久化 / 重试 / 并发控制 / 可观测性 / 部署复杂度 / 学习成本）。
       按 {语言} 生态取主流候选（如 Go 常见：裸 goroutine / asynq / NSQ / Kafka / RabbitMQ / go-quartz；
       其他语言按其生态对应列出）。
    2. **逐个排除分析**：每个被排除的方案，说明为何不选（部署成本 / 需自行实现重试 / 过度设计 / 生态不适配）。
    3. **选择**：选中的方案——核心优势表 + 不足与应对表。

    ### 三、架构设计决策
    1. task 层在目录结构中的位置、与 handler 的关系（进程隔离 / 对称 / 职责清晰）。
    2. 是否引入 Service 层（遵循现有架构哲学，不引入不必要的抽象）。
    3. 基础设施共享（DB / 客户端初始化放 config 等共享层）。
    4. Worker / 消费者配置（并发数、队列优先级）。

    ### 四、最佳实践
    - task handler 编写规范：幂等性、快速失败、状态标记（重试耗尽置 FAILED 让前端感知）、日志、超时可预期
    - 错误处理策略：失败 → 自动重试（指数退避）→ 重试耗尽 → 标记失败
    - 新增任务的标准流程（写文件 → 注册 → 入队）
    - 监控与运维（队列深度、失败率、告警）

    ### 五、迁移风险与应对
    当前异步实现迁移到新方案的风险表 + 回滚方案。

    ## 输出要求

    写两个文件（直接落盘）：
    - `docs/standards/task-layer-rule.md`：整体架构、目录结构、任务定义模式、依赖方向、进程模型、配置、
      错误处理策略、新增任务清单（AI 直接照做）。
    - `docs/standards/task-layer-draft.md`：问题背景、方案对比、决策理由、最佳实践、迁移风险（人工追溯）。
