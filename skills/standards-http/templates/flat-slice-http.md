# 扁平业务切片 · HTTP handler 请求流转（prompt 模板）

## prompt 模板

    你是一位资深后端工程师，精通{语言}和业务驱动开发。请你基于项目信息，遵守架构原则，
    在此基础上给出一个完整请求从 HTTP Handler 到数据库的流转路径，并输出至 docs/standards/。

    ## 项目信息

    请阅读以下文件获取业务流程、数据结构、技术选型：
    - 业务流程描述：docs/product/business-flow.md
    - DB 设计文件：docs/specs/data/（table.sql 或 schema.json）
    - 一个示例 API：docs/specs/API/<模块>.yaml（选一个代表性接口）
    - 技术选型：docs/standards/tech-stack-rule.md
    - 目录结构：docs/standards/directory-rule.md

    ## 架构原则

    项目采用扁平业务切片架构，核心理念：业务代码零抽象，基础设施平铺。

    1. **handlers/（业务切片层）**
       - 职责：每个接口一个文件，包含完整的校验、业务逻辑、响应封装
       - 一个接口 = 一个函数 = 一个文件
       - 接口之间不共享业务逻辑，相似代码各写各的
    2. **业务逻辑全展开**
       - 每个 handler 内部按业务顺序依次调用：DB 操作、日志、队列、告警等
       - 不做跨接口的业务抽象，不做 Service 层拆分
       - 读一个文件 = 理解一个接口的全部逻辑
    3. **工具层（基础设施，平铺组件库）**
       - 日志库、队列库、告警库、LLM 库、地图库、DB 库等
       - 作为工具按需直接调用，不包装成 Service
       - 工具层内部可以有抽象，但对业务层透明
    4. **零抽象原则**
       - 两个 handler 有 90% 代码相似，也各自独立写
       - "相似"是观察者的视角，不是代码的结构约束
       - 重构成本 < 过早抽象带来的理解成本
    5. **路由**
       - 路由注册集中在 router.go

    ## 输出要求

    1. 从示例 API 中选一个接口，给出完整请求从 HTTP Handler 到数据库的流转路径（逐环节标注）
    2. 每个环节说明：在哪个文件、做什么、调用什么工具/库
    3. 覆盖：路由匹配 → 参数校验 → 业务逻辑（DB 操作/日志/队列/告警）→ 响应封装
