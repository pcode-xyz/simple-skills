## 二 ~ N、各用例定义

> 每个用例占一个二级章节（`## 二、UC-XXX-001：用例名称`），内部固定 10 个小节。
> 小节编号用 `用例序号.1` ~ `用例序号.10`（如 `2.1` ~ `2.10`）。

### X.1 用例名称

一句话。

### X.2 用例概述

1~3 句话说清楚：做什么、谁触发、有什么副作用。不展开细节。

### X.3 参与者（Actor）

| 参与者 | 类型 | 说明 |
|--------|------|------|
| 小程序用户 | 主要参与者 | 行程的创建者/参与者/查看者 |
| 小程序客户端 | 系统参与者 | 发起 HTTP 请求 |
| LLM服务 | 外部系统 | 仅在涉及外部服务时列出 |

### X.4 前置条件

编号列出调用前必须满足的条件，包括：
1. 认证状态（JWT 有效、token 已注入 context）
2. 资源状态（目标记录存在、未被删除）
3. 权限状态（用户具有对应角色）
4. 依赖状态（数据库连接正常、外部服务可用）

### X.5 后置条件

分成功/失败两段：
- **成功场景**：数据变更、状态流转、推送事件、返回内容
- **失败场景**：明确"不写入任何数据"或"不修改任何数据"

### X.6 主成功场景（基本流程）

编号列出完整步骤，每步说清三件事之一：
- **参数校验**：哪些字段、什么规则
- **数据操作**：用伪 SQL 说明（`SELECT/INSERT/UPDATE 表名 WHERE 条件`）
- **响应构造**：返回的关键字段

示例：

```
1. 客户端发送 POST /模块/动作，携带 Authorization: Bearer <token>，请求体：
   { "字段A": 值, "字段B": 值 }
2. 中间件链：requestlog → cors → ratelimit → auth(JWT验证, 注入user_id)
3. 参数绑定与校验：
   3.1 字段A > 0
   3.2 字段B 非空且长度 ≤ 255
4. 获取 userID = context("user_id")
5. 查询主表验证资源存在：
   SELECT * FROM 主表 WHERE id = ? LIMIT 1
   不存在 → 返回错误码
6. 验证用户权限：
   6.1 检查是否为创建者 → 通过
   6.2 否则查关联表确认角色 → 不具备 → 返回权限错误
7. 执行业务操作：
   INSERT/UPDATE 目标表 SET ... WHERE ...
8. 记录日志
9. 返回成功响应：
   { "code": 0, "data": { ... }, "message": "操作成功" }
```

### X.7 扩展流程（备选流程）

每个扩展用以下格式：

```
**扩展N：简短描述**
- 条件：什么情况下走这条路径
- 处理：具体怎么做
- 返回/后续：结果如何
```

> 说明：扩展流程是合法的替代路径，不是错误。例如"首次分页"、"已使用状态下仍可操作"。

### X.8 异常流程

| 异常场景 | 触发条件 | 拦截层 | 返回结果 |
|---------|---------|--------|---------|
| 未认证访问 | 无 token 或 token 过期 | JWT 中间件 | HTTP 401 |
| 参数缺失 | 请求体/Query 无必填字段 | 参数校验 | HTTP 400 |
| 资源不存在 | 主表查询无结果 | 业务校验 | code=错误码，message="..." |
| 权限不足 | 用户角色不满足 | 业务校验 | code=错误码，message="..." |
| 数据库异常 | INSERT/UPDATE 失败 | 异常捕获 | HTTP 500，记录日志 |

> 说明：只列真正可能发生的异常，不要凑数。

### X.9 业务规则

编号列出硬性约束，每条一句话说清规则本身。规则应来自业务视角，不要重复前置条件中的技术细节。

示例：
1. **内容长度限制**：content 最大 255 字符，超出返回 6003。
2. **权限规则**：仅创建者和参与者可操作，查看者返回 6002。
3. **状态流转**：PENDING → CONFIRMED，不可逆。
4. **幂等性**：重复操作同一资源返回成功或特定错误码。

### X.10 数据要求

分三张表说明：

**涉及的数据库表：**

| 表名 | 操作类型 | 说明 |
|------|---------|------|
| 主表 | SELECT | 验证资源存在 |
| 关联表 | SELECT | 验证用户权限 |
| 目标表 | INSERT/UPDATE | 写入/修改业务数据 |

**写入/更新字段（仅写操作）：**

| 字段 | 类型 | 说明 | 操作时的值 |
|------|------|------|-----------|
| status | VARCHAR(16) | 状态 | 'PENDING' |
| updated_at | DATETIME | 更新时间 | 当前时间 |

**查询条件字段（仅读操作）：**

| 字段 | 类型 | 说明 | 查询条件 |
|------|------|------|---------|
| trip_id | BIGINT UNSIGNED | 所属行程 | = 请求参数 |

## 写作原则

### 允许冗余

以下内容在多处出现是合理的：
- **鉴权要求**：在 X.4 前置条件、X.8 异常流程、Y.2 中间件依赖中均可提及
- **错误码**：在 1.2 号段分配、X.8 异常流程、Y.6 汇总中均可出现
- **权限规则**：在 X.9 业务规则、Y.4 权限矩阵中均可出现

### 禁止内容

- **时序图**：不画 ASCII 时序图，容易画错且维护成本高
- **真实代码**：不写 Go 代码，用伪代码或伪 SQL 描述即可
- **模块级技术要点的逐用例重复**：文件路径、中间件链等共性内容只在模块汇总写一次

### 质量检查清单

- [ ] 每个用例的 10 个小节是否齐全（空节删除，不留空壳）
- [ ] 主成功场景的步骤是否覆盖"参数校验 → 权限校验 → 数据操作 → 响应构造"全链路
- [ ] 异常流程是否只列真实可能发生的情况
- [ ] 业务规则是否从业务视角描述（而非重复技术实现细节）
- [ ] 数据要求的字段表是否与主成功场景中的操作一致
- [ ] 模块汇总的错误码是否与总览和各用例一致
- [ ] 权限矩阵是否覆盖所有用例 × 所有角色
