# Task-UCS 转测试提取规范

> 本规范定义如何从 task-UCS（异步任务用例规约）系统性提取测试用例。
> **语言 / 任务方案 / 架构风格以技术推演结论文档为准**（tech-stack-rule / task-layer-rule / directory-rule）。
> 本规范只定义**提取方法论**（通用）；具体惯例按 §0 映射表取值。

---

## 〇、按技术推演取惯例（先读 tech-stack-rule / task-layer-rule / directory-rule，再按此取）

### 0.1 任务入口与调用方式（按 task-layer-rule）

task 层通常无 HTTP 接口，测试**直接调用任务入口**，一般不做 HTTP E2E：

| 任务方案 | 入口调用 | 说明 |
|---------|---------|------|
| Go + asynq | `HandleXxxTask(ctx, *asynq.Task)` | 直接调 |
| Node + BullMQ / Agenda | processor / job 处理函数 | 直接调 |
| Rust + 队列 | 任务处理函数 | 直接调 |
| Python + celery | task 函数 | `.apply`（同步）或 `.delay`（入队）按需 |

> 具体以 task-layer-rule.md 为准。

### 0.2 语言惯例（按 tech-stack-rule）

| 语言 | 测试框架 | 文件命名 | 函数/用例组织 | Mock 机制 |
|------|---------|---------|--------------|-----------|
| Go | testify、go-cmp | 集成 `{task}_integration_test.go`、单元 `{task}_test.go` | `Test<HandleFunc>_<TASK编号>_<场景>`，纯函数表驱动 + t.Run | 包级函数变量替换 |
| Node/TS | vitest、jest | `{task}.integration.test.ts`、`{task}.test.ts` | `describe`/`it`，`test.each` 参数化 | 框架内置 mock |
| Rust | 内置 + assert | 同文件 `#[cfg(test)] mod tests` 或 `{task}_test.rs` | `#[test]`/`#[tokio::test]`，参数化 `#[test_case]`/循环 | mockall |
| Python | pytest | `test_{task}.py` | pytest 函数，`@pytest.mark.parametrize` | monkeypatch |

### 0.3 目录（按 directory-rule）

任务层目录位置、与 handler 的关系以 directory-rule / task-layer-rule 为准（**不预设为 `task/`**）。

### 0.4 竞态检测（按语言）

Go `-race`；Node `vitest --pool threads` 等并发模式；Rust `cargo test`（默认单线程，并发用 tokio test）；Python `pytest-xdist` 或并发库。

## 一、规范定位

与接口（HTTP handler）测试提取的关系：

| 维度 | 接口测试提取 | 本规范（任务） |
|------|--------------|---------------|
| 适用对象 | 按 directory-rule 的接口层（如 handlers/、controller/、api/） | 按 directory-rule 的任务层 |
| 入口触发 | HTTP 请求（按框架测试模式） | **直接调用任务入口**（见 §0.1） |
| 断言对象 | HTTP 状态 / 响应体 / 业务码 | **DB 状态字段 + Redis 状态 + 外部服务调用 + 队列状态** |
| 外部依赖 | 一般只有 DB | DB + Redis + 外部服务（LLM/API 等，需 Mock）+ 队列 |
| 权限矩阵 | 通常需提取 | 通常不涉及（Worker 无角色概念） |
| 并发安全 | 可选 | **必提取**（分布式锁是核心机制） |
| 状态机 | 有 | **必提取**（任务状态 / 资源状态流转） |

**共同原则**：
- 测试用例从 task-UCS 提取，不凭空设计
- 1 个 task-UCS 文档 ↔ 1 个任务文件 ↔ 该文件下的测试文件
- task-UCS 中每个结构化章节均对应特定测试维度，无遗漏

## 二、task-UCS 文档结构

### 2.1 用例章节（每个任务独立一章）

每个任务包含固定子节，**6 个直接产出测试用例**：

| 子节 | 测试价值 | 优先级 |
|------|---------|--------|
| 主成功场景 | ✅ **高**：Happy Path 测试来源，断言 DB 状态变更 | 必提取 |
| 扩展流程 | ✅ **高**：分支/非致命错误路径测试来源 | 必提取 |
| 异常流程 | ✅ **高**：负向测试来源（fatal 错误路径） | 必提取 |
| 业务规则 | ✅ **高**：规则验证测试来源（锁、回滚、覆盖策略等） | 必提取 |
| 数据要求 | ✅ **中**：多表写入一致性测试来源 | 按需提取 |
| 前置/后置条件 | ⚠️ **低**：辅助推断 setup 和断言内容 | 参考 |

### 2.2 任务特有章节

| 子节 | 测试价值 | 优先级 |
|------|---------|--------|
| 分布式锁键 | ✅ **高**：并发安全测试来源（锁存在/清理/超时） | 必提取 |
| Payload 结构 | ✅ **中**：payload 校验测试来源 | 按需提取 |
| 广播消息结构 | ✅ **中**：Pub/Sub 消息内容断言来源 | 按需提取 |
| 摘要/统计计算规则 | ✅ **高**：纯函数单元测试来源 | 必提取 |
| 外部依赖表 | ✅ **高**：Mock 范围定义来源 | 必提取 |

## 三、提取规则

### 3.1 主成功场景 → Happy Path

**提取方式**：将场景中的每个步骤转化为 DB 状态断言。

```
task-UCS 步骤              →    测试断言
─────────────────────────────────────────────────────
1. 查询待处理数据          →    setup：写入待处理测试数据
2. 调用外部服务（LLM 等）  →    Mock 返回固定结果（无需真实调用）
3. 调用外部服务（地图等）  →    Mock 返回固定坐标
4. 更新数据状态            →    断言：状态字段正确，推断字段正确
5. 广播结果                →    断言：广播被调用，消息内容正确
6. 清理锁键                →    断言：锁键已删除
```

### 3.2 扩展流程 → 分支测试

每个扩展条件对应一个分支用例，重点关注**非致命错误路径**和**部分成功**：

| 扩展流程类型 | 测试内容 | 示例 |
|------------|---------|------|
| 空数据提前返回 | 无待处理数据时静默成功，不报错 | 无待处理 → 任务返回 nil |
| 外部服务降级 | 外部服务失败时的降级行为 | 外部失败 → 字段为默认值，仍标记完成 |
| 非致命错误 | 部分操作失败不阻断主流程 | 次要字段更新失败 → 主流程仍完成 |
| 外部特殊返回 | 非预期结果的处理 | NeedsMoreInfo → 状态变中间态，不写结果 |

### 3.3 异常流程 → 负向测试

每个 fatal 异常条件对应一个负向用例，**必须同时断言失败状态表**：

```
异常条件                   →    测试输入                  →    断言
──────────────────────────────────────────────────────────────────────────────
外部服务失败               →    Mock 返回 error           →    执行记录.status = 'failed'
                                                          →    错误信息含关键字
                                                          →    数据状态回滚（如 PENDING）
结果校验失败               →    Mock 返回非法格式          →    执行记录.status = 'failed'
                                                          →    结果表无新记录
DB 查询失败                →    注入错误                   →    任务返回 error（触发重试）
payload 格式错误           →    非法 payload               →    任务立即返回 error
```

**关键原则**：
- **fatal 错误**（主流程中断）：必须断言执行记录 status = failed + 错误信息
- **非 fatal 错误**（部分失败容忍）：必须断言主流程**仍然完成**，只有局部日志记录

### 3.4 业务规则 → 规则验证测试

| 业务规则类型 | 测试内容 | 示例 |
|------------|---------|------|
| 分布式锁（幂等保护） | 锁存在时的行为 + 锁清理时机 | 任务执行中锁存在；任务结束（无论成败）锁被清理 |
| 状态回滚 | fatal 错误时状态完全回滚 | 外部失败 → 中间状态回滚为初始态 |
| 非 fatal 错误容忍 | 部分失败不阻断主流程 | 次要字段更新失败，主数据仍写入 |
| Upsert 覆盖策略 | 重复执行结果可预期 | 同一资源两次处理，第二次覆盖第一次 |
| 来源唯一性 | 结果只来自指定来源 | 外部失败时用默认值，不使用其他来源推断值 |
| 上下文限制 | 数量边界行为 | 超出上限只取最新 N 条 |

### 3.5 分布式锁 → 并发安全测试

从分布式锁键章节提取竞态条件，用**竞态检测**（§0.4）运行：

```
并发场景                       →    测试方式
───────────────────────────────────────────────────────────────────
同一资源并发触发              →    并发调用任务入口，断言：
                                  第二次发现无待处理数据（已被第一次处理完），
                                  或验证锁键机制（SETNX 语义）
                                  状态最终为终态（无中间态残留）
```

> 完整并发测试需要真实 Redis（按语言容器化/Mock 方案），或验证锁键的原子性。

### 3.6 数据要求 → 多表写入一致性测试

| 数据操作类型 | 测试内容 | 示例 |
|------------|---------|------|
| 多表写入（fatal） | 任一步骤失败，验证各表状态符合预期 | 结果表写入成功 + 记录表更新失败 → 状态不一致（已知风险） |
| 多表写入（非 fatal） | 非 fatal 步骤失败，主表数据仍正确 | 次要表更新失败 → 主表仍写入 |
| Upsert 幂等性 | 重复执行不产生重复记录 | 同一资源执行两次，结果表只有一条 |
| 状态回滚 | fatal 错误后所有中间状态已清理 | 外部失败 → 状态全部回到初始态，无中间态残留 |

### 3.7 状态流转 → 状态机测试

```
合法转换（主成功场景后应达到）：
  资源: 初始态 → 处理中 → 完成     →    断言：最终状态 = 完成
  执行记录: pending → completed    →    断言：status = completed，结果非空
  执行记录: pending → failed       →    断言：status = failed，错误信息非空

异常后状态（fatal 错误后应回滚）：
  资源: 处理中 → 初始态（失败）     →    断言：无处理中状态残留
  执行记录: 无 → failed            →    断言：新增 failed 记录
```

### 3.8 摘要/统计计算规则 → 纯函数单元测试

从摘要统计计算规则章节直接提取纯函数测试，无需 DB/Redis/Mock：

```
边界值：空输入 / 单条 / 多条 / 超限
计算精度：距离/时长等数值计算允许误差
```

## 四、测试覆盖矩阵

每个 task-UCS 完成后，用此矩阵自检：

| 测试维度 | 提取来源 | 断言要点 |
|---------|---------|---------|
| Happy Path | 主成功场景 | DB 各表字段正确 + 锁清理 + 广播消息内容 |
| 分支逻辑 | 扩展流程 | 非致命错误路径主流程仍完成 + 降级字段值正确 |
| fatal 负向 | 异常流程（fatal） | 执行记录 status=failed + 错误信息含关键字 + 状态回滚完成 |
| 非 fatal 负向 | 扩展流程（非致命） | 主表数据正确 + 局部表数据未更新 |
| 分布式锁 | 业务规则（锁） | 任务成功/失败后锁键均被清理 |
| 状态回滚 | 业务规则（回滚） | fatal 错误后无中间状态残留 |
| 状态机 | 业务规则（状态流转） | 合法转换达到目标状态，非法状态残留不存在 |
| 多表一致性 | 数据要求 | Upsert 幂等 + 各表状态符合 fatal/non-fatal 预期 |
| 纯函数 | 摘要统计计算规则 | 边界值 + 计算精度 |
| 并发安全 | 分布式锁 + 业务规则 | 竞态检测通过 + 锁机制保证幂等 |

## 五、测试类型选择

| 测试维度 | 测试类型 | 说明 |
|---------|---------|------|
| 纯函数（计算规则等） | 单元测试 | 无需 Mock |
| Happy Path / 分支 / 负向（含 DB 状态变更） | 集成测试 | 真实 DB + 外部服务 Mock |
| 分布式锁 / 并发安全 | 集成测试 | 真实 Redis + 竞态检测 |
| 状态机 / 状态回滚 | 集成测试 | 真实 DB + Redis |
| 广播 / 队列断言 | 集成测试 | 真实消息/队列，订阅验证内容 |

**不推荐 HTTP E2E**：task 层通常无 HTTP 接口，直接调用任务入口（§0.1）。

## 六、Mock 策略

task 层外部依赖比接口层复杂，需明确 Mock 范围：

| 外部依赖 | 测试中处理方式 | 说明 |
|---------|--------------|------|
| 数据库 | **真实 DB**（按语言容器化方案） | 需要验证真实 DB 状态，不宜 Mock |
| Redis / 消息中间件 | **真实**（容器化） | 锁机制和广播需真实验证 |
| 外部服务（LLM/地图/API 等） | **Mock / 替换** | 抽象为可替换函数/接口，测试注入固定返回值或错误 |

**Mock 实现建议**：将外部调用抽象为可替换函数/接口（Go 包级函数变量；Node 框架 mock；Rust mockall；Python monkeypatch），测试时替换并在用例结束恢复。

## 七、测试文件规范

按 §0.2 的语言映射取文件命名 / 函数命名 / 用例组织。通用原则：
- 测试文件与任务源码同目录（按语言惯例）
- 命名与**已有测试文件不冲突**
- 集成场景独立函数，开头清库 + Mock（用例结束恢复）
- 函数命名带 `<TASK编号>_<场景>` 便于追溯（如 `Test<HandleFunc>_TASK_CHAT_001_HappyPath`，按语言惯例）

## 八、task-UCS 测试提取快速参考

| task-UCS 章节 | 提取的测试项 |
|---|---|
| 任务名称/概述/参与者 | — 不产出测试（参与者确定 Mock 范围） |
| 前置条件 | 辅助推断 setup（测试数据准备） |
| 后置条件 | 辅助推断断言（成功/失败的 DB 状态） |
| 主成功场景 | ✅ Happy Path 测试（每步 → 一个 DB 断言） |
| 扩展流程 | ✅ 分支测试（每个扩展 → 一个分支用例） |
| 异常流程 | ✅ 负向测试（每个 fatal 异常 → 一个负向用例） |
| 业务规则 | ✅ 规则验证测试（锁/回滚/覆盖/唯一性 → 各一个用例） |
| 数据要求 | ✅ 多表一致性测试 + 状态回滚测试 |
| 外部依赖 | 辅助确定 Mock 范围（不直接产出测试） |
| Payload 结构 | 辅助构造测试输入（payload 校验用例，按需） |
| 广播消息结构 | ✅ Pub/Sub 消息内容断言（按需） |
| 摘要统计计算规则 | ✅ 纯函数单元测试 |
