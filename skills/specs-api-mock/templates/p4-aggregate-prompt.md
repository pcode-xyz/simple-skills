## 任务

写入下方「## 报告路径」指定的文件（先 mkdir -p docs/specs/review）。严格按下面顺序与结构：

### 1. 开头一句话结论（报告第一行，不加标题，就是最重要的一句）

一句大白话说清三件事：demo 现在什么状态、接口够不够用、最要紧差在哪。
例：「demo 已全部改线接到接口 mock，file:// 能直接打开；接口定义基本够用，只剩 6 处缺接口（其中 1 处不补没法接真后端、5 处可延后），另有 8 处"有接口但 demo 还没用"。」

### 2. §0 这份报告是什么（2-3 句，写给第一次看的人）

- 做了什么：把 demo 的假数据换成"按接口定义生成的 mock"，逐页对照"页面要什么数据 / 接口能给什么数据"。
- 四个状态各一句话（用上面的白话对照）。
- 怎么读：第 1 节是你接下来要拍板的事；第 2 节每页一眼状态；第 3 节接真后端时核对；第 4 节改某个接口前看影响面；第 5-6 节技术细节。

### 3. §1 要你拍板：缺接口的（核心，按行动分组）

把全部缺口按「**必须补** / **建议补** / **可延后** / **单独立项**」分 4 组，按此顺序排列；每组前用一句加粗大白话标题（如「**必须补（不补没法接真后端）**」）。

每行表格：`| 缺什么（人话，先说要什么能力，别先甩 RPC 名） | 影响页面 | 期望接口（技术名+关键字段） | 建议 |`。

- 「缺什么」列必须人话优先：先写页面/用户缺了什么能力，再括注技术名；不许让读者第一眼看到的是 RPC 名。
- 「建议」列从 4 个分组取值，与所在分组一致。
- 分组依据 = 对输入的分类归纳（契约确缺的、契约已登记待定的、可客户端绕过的），不得臆造。

### 4. §2 每页一眼状态

`| 页面 | 一句话状态（人话） | 已接 | 缺接口 |`（表头注明「逐页计数」）。

- 「一句话状态」= 这页接得怎么样 + 最要紧的缺口是什么，**不许整行黑话**。
- 只留 已接 / 缺接口 两列数字（有接口未接、纯本地的数字不在此列，避免与全局口径打架）。

### 5. §3 有接口但 demo 还没用（接真后端时逐项核对，不是现在拍板）

`| 数据访问（人话） | 对应接口（技术） | 涉及页 |`。

### 6. §4 跨接口总览（改某个接口前，先看它的影响面）

从「## 对照存档」的结构化 JSON 里把各页数据访问**按接口（rpc）分组**，逐接口列出：使用页、各页要什么、状态。**RPC 名/字段一律以对照存档数据为据，不臆造。**

`| 接口（技术） | 使用页 | 各页要什么（人话 + 关键字段） | 备注（多页需求差异 / 关联 gap） |`。

- 「各页要什么」：人话先写该页拿这接口干什么，再括注它用到的关键契约字段；
- 「备注」：多页共用的接口必须标出各页需求是否一致（用的字段不同 / 调用形态不同 / 某页缺字段），这就是改接口前的影响面判断；有 gap 关联的给 G#；
- 只列被页面实际使用的接口；未被任何页面使用的接口不列（死接口排查归开发后 `review` 的范畴）。

### 7. §5 接口格式校验结论

一句话：mock 与接口定义是否严格一致、修了几轮、残留几处。残留问题逐条人话说明（缺哪个字段、影响什么），标为风险。
